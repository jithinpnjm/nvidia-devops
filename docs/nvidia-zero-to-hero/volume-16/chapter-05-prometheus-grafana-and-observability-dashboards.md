## Introduction

In Chapter 4, we enabled the DCGM Exporter. The Exporter simply exposes data on an HTTP endpoint. If nothing reads that data, it is lost forever.

To make the data useful, we must build a robust **Observability Pipeline**. The industry standard for cloud-native infrastructure is **Prometheus** (for data scraping and storage) and **Grafana** (for visualization).

However, monitoring an AI cluster is not like monitoring a web cluster. The sheer volume of telemetry generated by thousands of GPUs (especially when monitoring at the fractional MIG instance level) will easily overwhelm a default Prometheus installation, causing massive blind spots exactly when the system crashes.

## 1. The Prometheus Architecture for AI

Prometheus operates on a "pull" model. Every 15 seconds, it reaches out to the DCGM Exporter on every single node, downloads the text metrics, and stores them in its Time-Series Database (TSDB).

**The Cardinality Explosion:**
Prometheus tracks data using labels (e.g., `pod="inference-abc", gpu="0", mig_profile="1g.10gb"`). Every unique combination of labels creates a new time-series. 
In a Kubernetes cluster where pods are constantly spinning up and down (creating new pod names), the number of time-series explodes. This is called **High Cardinality**. It will consume all the RAM on the Prometheus server and crash it.

**The Architectural Fix (Federation):**
A Senior Architect never uses a single Prometheus server for a massive AI cluster. They use **Prometheus Federation** or a highly scalable remote storage backend like Thanos or Cortex. 
You run a lightweight Prometheus agent on every rack. Those agents scrape the local DCGM exporters, aggregate the data, and send it to a massive, centralized data lake for long-term storage and Grafana querying.

## 2. Designing the "Golden Signals" Dashboard

Grafana is useless if it is cluttered with 500 meaningless graphs. A dashboard must be designed to guide an SRE to the root cause of an incident in under 60 seconds.

**The 4 Pillars of an AI Dashboard:**
1.  **Cluster Health (The Top Level):** How many GPUs are currently `Allocatable` in Kubernetes? How many nodes are cordoned? Are there any active XID hardware errors?
2.  **Utilization (The ROI Level):** What is the global `DCGM_FI_PROF_SM_ACTIVE` percentage? Are we wasting money?
3.  **Thermal / Power (The Infrastructure Level):** Are any GPUs hitting their thermal limit (`DCGM_FI_DEV_CLOCK_THROTTLE_REASONS`)? This indicates a catastrophic HVAC failure in the data center.
4.  **Network (The Bottleneck Level):** NVLink bandwidth and PCIe RX/TX throughput. If computation is low but network is high, the job is bottlenecked on `AllReduce` rings.

## 3. The Power of PromQL

To build these dashboards, you must master PromQL (Prometheus Query Language). 

*Example:* You want to know the total power consumption of the cluster, but you only want to measure power consumed by the Finance department's models. 

Because the DCGM Exporter automatically injected Kubernetes metadata, the query is simple:
`sum(DCGM_FI_DEV_POWER_USAGE{namespace="finance"})`

This single query allows the FinOps team to execute precise chargeback based on literal electrical consumption, rather than estimated software allocation.

## Customer Scenario (Senior Level)

**The Situation:**
An SRE team at a large enterprise builds a Grafana dashboard using DCGM metrics. When they view the last 1 hour of data, the dashboard loads instantly. When the CFO asks to see the GPU utilization trend over the last 30 days to justify a new hardware purchase, the Grafana dashboard spins for 2 minutes and then crashes with a `504 Gateway Timeout`. The team blames Grafana.

**The Senior Architect Response:**
"Grafana is not the problem; the underlying Prometheus architecture is fundamentally incapable of handling the scale of historic AI telemetry queries.

When you query 30 days of high-resolution GPU telemetry across a 500-node cluster, Grafana asks Prometheus to retrieve and mathematically aggregate billions of individual data points. A standard, standalone Prometheus server stores data locally and is optimized for short-term, real-time alerting, not massive historical data warehousing. The query exhausts the Prometheus server's CPU and RAM, causing the timeout.

To fix this, we must implement a **Long-Term Storage (LTS)** architecture for our metrics. 

We will deploy a system like **Thanos** or **VictoriaMetrics** alongside Prometheus. Prometheus will continue to scrape the real-time DCGM metrics, but it will immediately offload the historical blocks of data into an S3 Object Store. 
Crucially, we will configure Prometheus **Recording Rules**. Instead of asking Grafana to aggregate the data on the fly, Prometheus will pre-calculate the average GPU utilization per namespace every hour, and store that tiny, summarized metric. 

When the CFO queries the 30-day dashboard, Grafana will query the pre-calculated, summarized metrics from the Thanos S3 backend, loading the multi-month report in milliseconds without stressing the real-time monitoring infrastructure."

As Kubernetes pods constantly spin up and down, the unique combinations of pod names and DCGM hardware metrics generate millions of new, unique time-series entries. This consumes massive amounts of RAM, eventually crashing the Prometheus server).*

**Architecture:** How does the integration of DCGM Exporter and Prometheus enable precise FinOps chargeback models? *(Hint: The DCGM Exporter automatically enriches the raw hardware metrics (like Wattage or Tensor Core utilization) with Kubernetes metadata, specifically the Namespace and Pod labels.
